# 迁移架构

## 结论

可行，但不应把 8 万多行 MEL 一次性机器翻译成一个同样巨大的 Python 文件。目标是保持行为的“绞杀式迁移”：原 MEL 在一段时间内仍是基准实现，Python 每次接管一个边界清楚、可对比的能力。

## 为什么不像编译产物

当前 `AdvancedSkeleton.mel` 具有可读变量名、功能注释、版本兼容分支、直接构建 Maya UI 的命令、历史注释代码和大量独立 `global proc`。这些特征更符合长期手工维护并发布为单文件的 MEL 工具。即使作者内部可能使用文本拼接或发布脚本，核心文件里也没有足以证明“由结构化工程编译生成”的映射、模块标记或稳定生成边界。

套件层面确实存在发布期代码注入的迹象：`panel.py` 带有明确的 `EMBED START/END` 标记，并会读取自身源码生成嵌入式脚本；`panel.mel`、`picker.mel`、两个 Selector 脚本与主文件各共享 298 个过程名。因此更准确的判断是：作者很可能使用了复制公共库或生成发布载荷的流程，但没有证据表明核心 8.5 万行 MEL 是从一套结构化 Python 源工程编译而来。

## 目标边界

```text
adv_py
├── application     # 用例编排、事务、进度、错误语义
├── domain          # FitSkeleton、构建选项、命名与验证规则
├── features
│   ├── body        # 身体 Fit / Build / ReBuild
│   ├── face        # 面部拟合、Build Step、表情与口型
│   ├── deform      # Skin、BlendShape、DeltaMush、Wrap
│   ├── mocap       # 动捕映射与连接
│   └── export      # FBX、Unreal、MetaHuman
├── maya            # maya.cmds / maya.api.OpenMaya 适配层
├── ui              # PySide 界面，只调用 application 用例
└── legacy          # 未迁移 MEL 的显式兼容边界
```

依赖方向固定为 `ui -> application -> domain`，Maya 与 Legacy 作为外围适配器注入。业务模块不直接读取 UI 控件，也不把全局 MEL 变量继续伪装成 Python 模块全局变量。

## 推荐迁移顺序

1. 冻结输入版本与哈希，生成过程清单和调用关系。
2. 先迁移无 UI、无 `eval`、无全局写入的叶子工具过程，例如命名、标签、数组与数学辅助逻辑。
3. 建立 Maya Scene Adapter，把节点查询与修改集中起来，并用 Undo Chunk 包住单个用例。
4. 迁移 FitSkeleton 的读取、校验和单个编辑动作。
5. 迁移 Body Build/ReBuild 的阶段编排；每一阶段保留旧 MEL 对照入口。
6. 再处理 Deform、Export、MoCap；Face 最后迁移，因为它规模大、动态命令与 UI 状态耦合最重。
7. 所有功能稳定后再替换主 UI，最后移除 Legacy Bridge。

## 两阶段开发边界

### 第一阶段：Maya Python 重构

主线只处理 Maya：从 MEL 清单与调用关系中选择边界清楚的能力，先建立 Python 领域模型与 Maya Scene Adapter，再用本机授权 ADV 行为做结果对照。每个切片必须能在 Maya 中独立运行、复检和回滚；未迁移部分继续通过明确的 Legacy Bridge 调用，不做全量机械翻译。

第一阶段的完成门槛不是“过程数量翻译完”，而是核心身体流程已经形成稳定模块：Fit 数据读取与校验、骨架生成、IK/FK、控制器、重建、基础变形及保存/加载合同都有 Maya 侧可运行用例；核心逻辑不依赖 UI 状态或 MEL 全局变量；主流程不再需要大范围回退到单体 MEL。

### 第二阶段：迁移到 Blender

只有通过第一阶段门槛的功能才进入 Blender。迁移单位是已经验证的 Python 语义合同，而不是 MEL 过程；Blender 适配器负责 Armature、约束、驱动、坐标系和数据持久化差异。Maya 仍作为行为基准，但第二阶段不改变已经稳定的核心语义来迁就某个 Blender API。

当前两节骨架和三关节 IK/FK Blender 实现仅用于证明架构方向可行，暂时冻结功能范围。除修复防回归问题外，不在第一阶段继续增加 Blender 控制器、蒙皮、UI 或高级 limb 能力。

## 不能依赖纯自动转换的部分

- MEL 全局变量跨过程共享，Python 模块命名空间不会自动等价。
- 字符串拼接的 `eval`、`evalDeferred`、按钮回调需要改成显式 callable。
- MEL 空数组、越界填充、命令返回值与 `maya.cmds` 的 `None` 行为不同。
- `catch/catchQuiet`、隐式选择集、当前父 UI 和 Maya 全局状态都需要明确建模。
- 过程之间存在大量按名字调用，机械分文件不会自动得到合理模块边界。

## 每次迁移的轻量验收

每个切片只保留三层证据：纯 Python 单元测试、同一输入场景的旧/新状态快照对比、一次独立 Maya GUI 生命周期烟雾测试。不会为每个过程建立重量级门禁；高风险构建与文件写入才增加专门场景。
