# 迁移架构

## 结论

可行，但不应把 8 万多行 MEL 一次性机器翻译成一个同样巨大的 Python 文件。目标是保持行为的“绞杀式迁移”：原 MEL 在一段时间内仍是基准实现，Python 每次接管一个边界清楚、可对比的能力。

## 为什么不像编译产物

当前 `AdvancedSkeleton.mel` 具有可读变量名、功能注释、版本兼容分支、直接构建 Maya UI 的命令、历史注释代码和大量独立 `global proc`。这些特征更符合长期手工维护并发布为单文件的 MEL 工具。即使作者内部可能使用文本拼接或发布脚本，核心文件里也没有足以证明“由结构化工程编译生成”的映射、模块标记或稳定生成边界。

套件层面确实存在发布期代码注入的迹象：`panel.py` 带有明确的 `EMBED START/END` 标记，并会读取自身源码生成嵌入式脚本；`panel.mel`、`picker.mel`、两个 Selector 脚本与主文件各共享 298 个过程名。因此更准确的判断是：作者很可能使用了复制公共库或生成发布载荷的流程，但没有证据表明核心 8.5 万行 MEL 是从一套结构化 Python 源工程编译而来。

## 目标边界

```text
adv_py
├── application     # 用例编排、事务、进度、错误语义
├── domain          # FitSkeleton、构建选项、命名与验证规则
├── features
│   ├── body        # 身体 Fit / Build / ReBuild
│   ├── face        # 面部拟合、Build Step、表情与口型
│   ├── deform      # Skin、BlendShape、DeltaMush、Wrap
│   ├── mocap       # 动捕映射与连接
│   └── export      # FBX、Unreal、MetaHuman
├── maya            # maya.cmds / maya.api.OpenMaya 适配层
├── ui              # PySide 界面，只调用 application 用例
└── legacy          # 未迁移 MEL 的显式兼容边界
```

依赖方向固定为 `ui -> application -> domain`，Maya 与 Legacy 作为外围适配器注入。业务模块不直接读取 UI 控件，也不把全局 MEL 变量继续伪装成 Python 模块全局变量。

## 推荐迁移顺序

1. 冻结输入版本与哈希，生成过程清单和调用关系。
2. 先迁移无 UI、无 `eval`、无全局写入的叶子工具过程，例如命名、标签、数组与数学辅助逻辑。
3. 建立 Maya Scene Adapter，把节点查询与修改集中起来，并用 Undo Chunk 包住单个用例。
4. 迁移 FitSkeleton 的读取、校验和单个编辑动作。
5. 迁移 Body Build/ReBuild 的阶段编排；每一阶段保留旧 MEL 对照入口。
6. 再处理 Deform、Export、MoCap；Face 最后迁移，因为它规模大、动态命令与 UI 状态耦合最重。
7. 所有功能稳定后再替换主 UI，最后移除 Legacy Bridge。

## 两阶段开发边界

### 第一阶段：Maya Python 重构

主线只处理 Maya：从 MEL 清单与调用关系中选择边界清楚的能力，先建立 Python 领域模型与 Maya Scene Adapter，再用本机授权 ADV 行为做结果对照。每个切片必须能在 Maya 中独立运行、复检和回滚；未迁移部分继续通过明确的 Legacy Bridge 调用，不做全量机械翻译。

第一阶段的完成门槛不是“过程数量翻译完”，而是核心身体流程已经形成稳定模块：Fit 数据读取与校验、骨架生成、IK/FK、控制器、重建、基础变形及保存/加载合同都有 Maya 侧可运行用例；核心逻辑不依赖 UI 状态或 MEL 全局变量；主流程不再需要大范围回退到单体 MEL。

### 第二阶段：迁移到 Blender

只有通过第一阶段门槛的功能才进入 Blender。迁移单位是已经验证的 Python 语义合同，而不是 MEL 过程；Blender 适配器负责 Armature、约束、驱动、坐标系和数据持久化差异。Maya 仍作为行为基准，但第二阶段不改变已经稳定的核心语义来迁就某个 Blender API。

当前两节骨架和三关节 IK/FK Blender 实现仅用于证明架构方向可行，暂时冻结功能范围。除修复防回归问题外，不在第一阶段继续增加 Blender 控制器、蒙皮、UI 或高级 limb 能力。

## Maya 切片 01：FitSkeleton 关节标签

首个 Maya-only 切片把标签文本、用例编排和 Maya 属性写入拆成三层。调用方显式传入关节列表与标签，不再读取当前选择或 UI 控件；application 层先解析全部关节，任何缺失、重名或非 joint 输入都会在修改前失败；Maya 适配器在一个 Undo Chunk 内写入 `drawLabel`、`type` 与自定义标签，并提供读取和隐藏操作。

该切片保留 Maya 标准 label type 语义，未知业务标签统一使用 Maya 的 Other 类型保存原文本。验证使用自行创建的关节，不读取 ADV 场景或资产。下一批 FitSkeleton 工作继续沿用同一边界，优先处理 Fit joint 元数据的读取与校验，不扩展 Blender。

## Maya 切片 02：Fit joint 元数据审计

第二个 Maya-only 切片把 `MayaJointLabelHost` 收拢为统一的 `MayaFitJointHost`。适配器负责把 Maya 动态属性转换为 `FitJointMetadata`，application 层只接收显式关节列表，核心审计不导入 Maya。

当前数据合同覆盖 Twist/Bendy、Inbetween/UnTwister、镜像开关、`childOfPart`、global 行为、世界朝向和 IK Local 模式。审计会报告 Twist 与 Inbetween 并存、依赖项缺失、负数量及范围越界。该用例完全只读；Maya 2024 验证确认读取和失败预检不会把场景标记为已修改。

## Maya 切片 03：声明式元数据变更

`FitJointPatch` 用字段和值描述期望状态，其中 `None` 明确表示删除属性。`EditFitJointMetadata.plan()` 会读取全部目标关节、预测变更后的完整状态、运行同一套核心审计，并返回逐关节、逐字段的前后差异；预览阶段不修改 Maya 场景。

`apply()` 只在计划非空时打开一个 Maya Undo Chunk。Maya 适配器按声明创建、更新或删除动态属性，application 随后重新读取所有目标字段；属性存在性或值不一致、以及最终审计失败都会在事务内部抛错并撤销本次修改。Maya 2024 自生成场景验证覆盖 Twist/Bendy 到 Inbetween 的模式切换、枚举属性、非法组合拦截、复检和一次 Undo 恢复。

## Maya 切片 04：层级快照与构建前校验

`MayaFitJointHost.capture_fit_hierarchy()` 解析唯一的 FitSkeleton transform，一次采集全部后代 joint 的完整 DAG 路径、直接父节点、本地位置和世界位置，并按父级优先稳定排序。Maya API 只存在于适配器；`InspectFitHierarchy` 把不可变快照交给纯 Python 核心审计。

当前构建前条件覆盖：恰好一个直接根关节、根名为 `Root`、根相对容器位于中心容差内、每个后代的直接父级也是快照内 joint、短名唯一、名称不以下划线分隔且不以数字开头，以及合成快照中的父链循环。命名空间只属于宿主路径，不参与业务短名比较。审计全程只读，既可返回完整问题列表，也可由调用方在正式构建前统一拒绝。

本切片刻意没有推断 `_L/_R` 等侧向后缀。现有证据只足以确认 Fit joint 的通用名称限制和中心判断；世界位置已保留在快照中，待镜像配对语义被独立验证后再增加规则，避免把其他 ADV 对象的命名习惯错误固化为 FitSkeleton 合同。

## Maya 切片 05：容器设置补齐

`FitSkeletonSettings` 用有序字段和值表达容器上的显示开关、构建选项、对象记录和 ReBuild 脚本文本。核心层负责类型、显示几何枚举和 `visGap` 范围；Maya 适配器负责属性名、Maya 数据类型及 keyable 状态，两者之间不共享 UI 控件或 MEL 全局变量。

`EnsureFitSkeletonSettings.plan()` 读取现有容器并列出缺失字段。已有字段类型错误或值非法时，预检直接失败；`apply()` 只在确有缺失字段时打开一个 Undo Chunk，逐项补齐后重新读取完整快照，同时确认已有值没有被改写。失败会撤销本次补齐。ReBuild 脚本在这个用例里只作为不透明字符串保存和复检，不会求值或执行。

显示间距默认值作为显式参数传入，默认 `0.75`，不读取 `optionVar` 或界面状态。这样既保留已确认的默认行为，也让未来配置来源由 application 调用方决定。Maya 2024 自生成场景验证覆盖只读预览、18 个缺失字段的增量补齐、已有值保留、脚本文本不执行、非法属性类型拦截和一次 Undo 恢复。

## Maya 切片 06：非破坏性容器创建

`FitContainerSpec` 描述根级短名、显示半径、Y/Z Up、环形语义和 Fit 显示样式。`CreateFitSkeleton.plan()` 从 Maya 适配器读取当前场景 Up Axis，并扫描整个场景中的同名节点；计划阶段不读取选择、不修改场景。任何类型的同名节点都会阻止执行，既不删除，也不依赖 Maya 自动改名。

执行阶段在一个 Undo Chunk 内创建根级圆环、应用宿主显示样式、锁定平移与旋转，并复用第五切片的设置合同补齐 21 项默认值。创建后重新读取容器状态和设置，检查根级路径、名称、形状、显示样式、零位姿、锁定通道、圆环平面与半径，以及设置所属节点和所有默认值；任一检查失败都会撤销整个创建事务。

Maya 适配器在创建曲线前保存当前选择并在命令结束后恢复。Maya 2024 自生成 Z-Up 场景验证确认计划只读、选择不变、同名二次创建被阻止、已有容器不受影响、一次 Undo 删除本次创建且无关节点继续存在。

## Maya 切片 07：自生成 Root/Spine 基础模板

本机清单显示完整身体 FitSkeleton 依赖外部模板导入，没有适合直接迁移的独立模板构建过程。本切片不解析模板文件，改用独立设计的 `FitTemplateSpec` 与三关节基线 `Root → Spine1 → Spine2`，为 Python 侧提供可运行的 Fit 编辑入口和合法测试素材。模板根据 Maya 当前 Y/Z Up 生成局部偏移，段长由调用方显式提供。

核心层检查唯一 `Root`、父级存在性、重复名称、循环、有限位置并生成稳定的父级优先顺序；创建后的不可变层级快照会再次与模板逐关节比较父级和局部位置。application 层要求目标容器已具备完整设置且尚无任何关节，并扫描整个场景中的同名节点。任一阻塞都在事务前返回，既不合并旧层级，也不自动改名。

执行阶段在一个 Undo Chunk 内逐级创建 joint 并写入 Maya 标准 Root/Spine 标签，随后复检层级、标签和容器设置未被改写。Maya 2024 自生成 Z-Up 场景验证确认计划只读、选择保持、重复创建被阻止、一次 Undo 只移除三个新关节，容器、设置和无关节点继续存在。

这个三关节基线只用于验证重构架构和后续 Fit 编辑，不声称等价于授权安装中的完整身体模板。下一切片继续 Maya-only，建立声明式 Fit joint 位置编辑、锁定通道预检与修改后复检，不推进镜像 limb 或 Blender。

## 不能依赖纯自动转换的部分

- MEL 全局变量跨过程共享，Python 模块命名空间不会自动等价。
- 字符串拼接的 `eval`、`evalDeferred`、按钮回调需要改成显式 callable。
- MEL 空数组、越界填充、命令返回值与 `maya.cmds` 的 `None` 行为不同。
- `catch/catchQuiet`、隐式选择集、当前父 UI 和 Maya 全局状态都需要明确建模。
- 过程之间存在大量按名字调用，机械分文件不会自动得到合理模块边界。

## 每次迁移的轻量验收

每个切片只保留三层证据：纯 Python 单元测试、同一输入场景的旧/新状态快照对比、一次独立 Maya GUI 生命周期烟雾测试。不会为每个过程建立重量级门禁；高风险构建与文件写入才增加专门场景。
