# 迁移架构

## 结论

可行，但不应把 8 万多行 MEL 一次性机器翻译成一个同样巨大的 Python 文件。目标是保持行为的“绞杀式迁移”：原 MEL 在一段时间内仍是基准实现，Python 每次接管一个边界清楚、可对比的能力。

## 为什么不像编译产物

当前 `AdvancedSkeleton.mel` 具有可读变量名、功能注释、版本兼容分支、直接构建 Maya UI 的命令、历史注释代码和大量独立 `global proc`。这些特征更符合长期手工维护并发布为单文件的 MEL 工具。即使作者内部可能使用文本拼接或发布脚本，核心文件里也没有足以证明“由结构化工程编译生成”的映射、模块标记或稳定生成边界。

套件层面确实存在发布期代码注入的迹象：`panel.py` 带有明确的 `EMBED START/END` 标记，并会读取自身源码生成嵌入式脚本；`panel.mel`、`picker.mel`、两个 Selector 脚本与主文件各共享 298 个过程名。因此更准确的判断是：作者很可能使用了复制公共库或生成发布载荷的流程，但没有证据表明核心 8.5 万行 MEL 是从一套结构化 Python 源工程编译而来。

## 目标边界

```text
adv_py
├── application     # 用例编排、事务、进度、错误语义
├── domain          # FitSkeleton、构建选项、命名与验证规则
├── features
│   ├── body        # 身体 Fit / Build / ReBuild
│   ├── face        # 面部拟合、Build Step、表情与口型
│   ├── deform      # Skin、BlendShape、DeltaMush、Wrap
│   ├── mocap       # 动捕映射与连接
│   └── export      # FBX、Unreal、MetaHuman
├── maya            # maya.cmds / maya.api.OpenMaya 适配层
├── ui              # PySide 界面，只调用 application 用例
└── legacy          # 未迁移 MEL 的显式兼容边界
```

依赖方向固定为 `ui -> application -> domain`，Maya 与 Legacy 作为外围适配器注入。业务模块不直接读取 UI 控件，也不把全局 MEL 变量继续伪装成 Python 模块全局变量。

## 推荐迁移顺序

1. 冻结输入版本与哈希，生成过程清单和调用关系。
2. 先迁移无 UI、无 `eval`、无全局写入的叶子工具过程，例如命名、标签、数组与数学辅助逻辑。
3. 建立 Maya Scene Adapter，把节点查询与修改集中起来，并用 Undo Chunk 包住单个用例。
4. 迁移 FitSkeleton 的读取、校验和单个编辑动作。
5. 迁移 Body Build/ReBuild 的阶段编排；每一阶段保留旧 MEL 对照入口。
6. 再处理 Deform、Export、MoCap；Face 最后迁移，因为它规模大、动态命令与 UI 状态耦合最重。
7. 所有功能稳定后再替换主 UI，最后移除 Legacy Bridge。

## 两阶段开发边界

### 第一阶段：Maya Python 重构

主线只处理 Maya：从 MEL 清单与调用关系中选择边界清楚的能力，先建立 Python 领域模型与 Maya Scene Adapter，再用本机授权 ADV 行为做结果对照。每个切片必须能在 Maya 中独立运行、复检和回滚；未迁移部分继续通过明确的 Legacy Bridge 调用，不做全量机械翻译。

第一阶段的完成门槛不是“过程数量翻译完”，而是核心身体流程已经形成稳定模块：Fit 数据读取与校验、骨架生成、IK/FK、控制器、重建、基础变形及保存/加载合同都有 Maya 侧可运行用例；核心逻辑不依赖 UI 状态或 MEL 全局变量；主流程不再需要大范围回退到单体 MEL。

### 第二阶段：迁移到 Blender

只有通过第一阶段门槛的功能才进入 Blender。迁移单位是已经验证的 Python 语义合同，而不是 MEL 过程；Blender 适配器负责 Armature、约束、驱动、坐标系和数据持久化差异。Maya 仍作为行为基准，但第二阶段不改变已经稳定的核心语义来迁就某个 Blender API。

当前两节骨架和三关节 IK/FK Blender 实现仅用于证明架构方向可行，暂时冻结功能范围。除修复防回归问题外，不在第一阶段继续增加 Blender 控制器、蒙皮、UI 或高级 limb 能力。

## Maya 切片 01：FitSkeleton 关节标签

首个 Maya-only 切片把标签文本、用例编排和 Maya 属性写入拆成三层。调用方显式传入关节列表与标签，不再读取当前选择或 UI 控件；application 层先解析全部关节，任何缺失、重名或非 joint 输入都会在修改前失败；Maya 适配器在一个 Undo Chunk 内写入 `drawLabel`、`type` 与自定义标签，并提供读取和隐藏操作。

该切片保留 Maya 标准 label type 语义，未知业务标签统一使用 Maya 的 Other 类型保存原文本。验证使用自行创建的关节，不读取 ADV 场景或资产。下一批 FitSkeleton 工作继续沿用同一边界，优先处理 Fit joint 元数据的读取与校验，不扩展 Blender。

## Maya 切片 02：Fit joint 元数据审计

第二个 Maya-only 切片把 `MayaJointLabelHost` 收拢为统一的 `MayaFitJointHost`。适配器负责把 Maya 动态属性转换为 `FitJointMetadata`，application 层只接收显式关节列表，核心审计不导入 Maya。

当前数据合同覆盖 Twist/Bendy、Inbetween/UnTwister、镜像开关、`childOfPart`、global 行为、世界朝向和 IK Local 模式。审计会报告 Twist 与 Inbetween 并存、依赖项缺失、负数量及范围越界。该用例完全只读；Maya 2024 验证确认读取和失败预检不会把场景标记为已修改。

## Maya 切片 03：声明式元数据变更

`FitJointPatch` 用字段和值描述期望状态，其中 `None` 明确表示删除属性。`EditFitJointMetadata.plan()` 会读取全部目标关节、预测变更后的完整状态、运行同一套核心审计，并返回逐关节、逐字段的前后差异；预览阶段不修改 Maya 场景。

`apply()` 只在计划非空时打开一个 Maya Undo Chunk。Maya 适配器按声明创建、更新或删除动态属性，application 随后重新读取所有目标字段；属性存在性或值不一致、以及最终审计失败都会在事务内部抛错并撤销本次修改。Maya 2024 自生成场景验证覆盖 Twist/Bendy 到 Inbetween 的模式切换、枚举属性、非法组合拦截、复检和一次 Undo 恢复。

## Maya 切片 04：层级快照与构建前校验

`MayaFitJointHost.capture_fit_hierarchy()` 解析唯一的 FitSkeleton transform，一次采集全部后代 joint 的完整 DAG 路径、直接父节点、本地位置和世界位置，并按父级优先稳定排序。Maya API 只存在于适配器；`InspectFitHierarchy` 把不可变快照交给纯 Python 核心审计。

当前构建前条件覆盖：恰好一个直接根关节、根名为 `Root`、根相对容器位于中心容差内、每个后代的直接父级也是快照内 joint、短名唯一、名称不以下划线分隔且不以数字开头，以及合成快照中的父链循环。命名空间只属于宿主路径，不参与业务短名比较。审计全程只读，既可返回完整问题列表，也可由调用方在正式构建前统一拒绝。

本切片刻意没有推断 `_L/_R` 等侧向后缀。现有证据只足以确认 Fit joint 的通用名称限制和中心判断；世界位置已保留在快照中，待镜像配对语义被独立验证后再增加规则，避免把其他 ADV 对象的命名习惯错误固化为 FitSkeleton 合同。

## Maya 切片 05：容器设置补齐

`FitSkeletonSettings` 用有序字段和值表达容器上的显示开关、构建选项、对象记录和 ReBuild 脚本文本。核心层负责类型、显示几何枚举和 `visGap` 范围；Maya 适配器负责属性名、Maya 数据类型及 keyable 状态，两者之间不共享 UI 控件或 MEL 全局变量。

`EnsureFitSkeletonSettings.plan()` 读取现有容器并列出缺失字段。已有字段类型错误或值非法时，预检直接失败；`apply()` 只在确有缺失字段时打开一个 Undo Chunk，逐项补齐后重新读取完整快照，同时确认已有值没有被改写。失败会撤销本次补齐。ReBuild 脚本在这个用例里只作为不透明字符串保存和复检，不会求值或执行。

显示间距默认值作为显式参数传入，默认 `0.75`，不读取 `optionVar` 或界面状态。这样既保留已确认的默认行为，也让未来配置来源由 application 调用方决定。Maya 2024 自生成场景验证覆盖只读预览、18 个缺失字段的增量补齐、已有值保留、脚本文本不执行、非法属性类型拦截和一次 Undo 恢复。

## Maya 切片 06：非破坏性容器创建

`FitContainerSpec` 描述根级短名、显示半径、Y/Z Up、环形语义和 Fit 显示样式。`CreateFitSkeleton.plan()` 从 Maya 适配器读取当前场景 Up Axis，并扫描整个场景中的同名节点；计划阶段不读取选择、不修改场景。任何类型的同名节点都会阻止执行，既不删除，也不依赖 Maya 自动改名。

执行阶段在一个 Undo Chunk 内创建根级圆环、应用宿主显示样式、锁定平移与旋转，并复用第五切片的设置合同补齐 21 项默认值。创建后重新读取容器状态和设置，检查根级路径、名称、形状、显示样式、零位姿、锁定通道、圆环平面与半径，以及设置所属节点和所有默认值；任一检查失败都会撤销整个创建事务。

Maya 适配器在创建曲线前保存当前选择并在命令结束后恢复。Maya 2024 自生成 Z-Up 场景验证确认计划只读、选择不变、同名二次创建被阻止、已有容器不受影响、一次 Undo 删除本次创建且无关节点继续存在。

## Maya 切片 07：自生成 Root/Spine 基础模板

本机清单显示完整身体 FitSkeleton 依赖外部模板导入，没有适合直接迁移的独立模板构建过程。本切片不解析模板文件，改用独立设计的 `FitTemplateSpec` 与三关节基线 `Root → Spine1 → Spine2`，为 Python 侧提供可运行的 Fit 编辑入口和合法测试素材。模板根据 Maya 当前 Y/Z Up 生成局部偏移，段长由调用方显式提供。

核心层检查唯一 `Root`、父级存在性、重复名称、循环、有限位置并生成稳定的父级优先顺序；创建后的不可变层级快照会再次与模板逐关节比较父级和局部位置。application 层要求目标容器已具备完整设置且尚无任何关节，并扫描整个场景中的同名节点。任一阻塞都在事务前返回，既不合并旧层级，也不自动改名。

执行阶段在一个 Undo Chunk 内逐级创建 joint 并写入 Maya 标准 Root/Spine 标签，随后复检层级、标签和容器设置未被改写。Maya 2024 自生成 Z-Up 场景验证确认计划只读、选择保持、重复创建被阻止、一次 Undo 只移除三个新关节，容器、设置和无关节点继续存在。

## Maya 切片 08：声明式 Fit joint 位置编辑

`FitJointPositionPatch` 以显式关节路径或唯一短名描述期望的本地位置。纯 Python 计划先审计完整 FitSkeleton 层级，再解析全部目标、过滤没有实际变化的轴，并检查这些轴在快照中是否可写；锁定或被连接驱动的变化轴会在事务前失败。Root 的本地 X 仍受中心容差约束。

Maya 层级快照现在额外记录每个 joint 的锁定轴和可写轴。适配器只对计划中的变化轴分别调用 `setAttr`，因此其他锁定轴不会造成无关阻塞，也不会被自动解锁或断开连接。批量写入位于一个 Undo Chunk；执行后重新采集层级和容器设置，确认节点集合、父级、短名、锁定/可写状态、未编辑的本地位置及所有目标值一致。

移动父关节会按 Maya DAG 正常带动后代世界位置，但后代本地位置保持不变。本切片不调用耦合 UI、临时节点与多种朝向分支的旧更新过程，也不自动重算 `jointOrient` 或刷新可视化几何。Maya 2024 自生成场景验证覆盖 Root 离中拦截、锁定轴拦截、双关节批量修改、选择保持、层级保持和一次 Undo 恢复。

## Maya 切片 09：简单单子链朝向

`FitOrientationSnapshot` 把层级、场景 Up Axis、jointOrient、rotate、世界轴和 jointOrient 可写状态组合成不可变输入。`FitOrientationRequest` 只接受显式目标；纯 Python 计划要求每个目标恰好有一个直接 joint 子级、rotate 为零、目标 jointOrient 可写，并要求全部后代 translate 可用于位置补偿。

朝向语义固定为本地 X 指向直接子级，本地 Y 尽量贴近场景正 Up。若 Aim 与 Up 近似平行，计划从其他世界正轴中确定性选择正交参考，并记录期望的世界 X/Y 轴。Maya 适配器使用显式 joint 路径执行朝向，不依赖选择；执行后恢复 Maya 隐式改写的直接子级 jointOrient，并按父到子顺序恢复全部后代世界位置。

application 在同一个 Undo Chunk 内按层级顺序应用多个目标，随后复检世界轴、零 rotate、所有 joint 世界位置、末端 jointOrient、层级结构、锁定/可写状态和容器设置。已达到期望轴向的目标不会重复写入，因此再次计划为空操作。

首次真实验证发现 Maya 会隐式改写直接子 joint 的 jointOrient；加入恢复后，第二次验证进一步发现后代世界位置需要显式补偿。两次失败都在事务内自动撤销。最终 Maya 2024 自生成 Z-Up 验证通过锁定预检、双关节朝向、末端保护、位置保持、选择保持、幂等计划和一次 Undo 恢复。

当前只支持无分支单子链和固定 X-Aim/Y-Secondary，不覆盖多子级选择、自由朝向、worldOrient 写入或镜像 limb。

## Maya 切片 10：worldOrient 朝向策略预检

`parse_world_orientation_policy` 将 `worldOrientUp` 的 Up/Down 与 `worldOrientForward` 的 Forward/Backward 解析为带正负号的本地轴方向；`free` 被保留为明确的自由 Forward，而不是偷偷替换为场景轴。解析会拒绝只有 Forward 没有 Up、未知枚举，以及 Up/Forward 使用同一本地轴的冲突配置。

Maya 朝向快照现在同时采集每个 joint 的可选元数据。简单单子链计划会在处理目标前解析 worldOrient；检测到该策略时，明确说明已识别的本地轴组合，并在事务开始前拒绝交给 X-Aim/Y-Secondary 写入器。这个边界避免两种语义被混写，也没有复制旧实现会自动修改冲突枚举的副作用。

本切片仅建立宿主无关策略合同和安全预检。后续 Maya-only 切片将为固定 Forward 组合建立独立的世界基准朝向计划、矩阵写入和 Undo 复检；`free`、World Match、轴交换与对称分支继续保持未实现。

## Maya 切片 11：固定 worldOrient 写入

`world_axes_from_orientation_policy` 把两条带正负号的本地轴约束展开为完整右手系世界 X/Y/Z 轴。当前证据对应世界 Up `+Y`、世界 Forward `+Z`，所以计划明确要求 Maya Y-Up；Z-Up 不做推断式换轴。`plan_world_fit_orientations` 只接受同时具有固定 Up/Forward 的单子链目标，并复用 jointOrient、rotate、子 jointOrient 和全部后代 translate 的可写预检。

`OrientWorldFitJoints` 与原 X-Aim 用例分离。Maya 适配器将计划出的正交世界矩阵写到目标 joint，再把 rotate 烘入 jointOrient，恢复直接子级 jointOrient，并按父到子顺序恢复后代世界位置。整个批次位于一个 Undo Chunk，执行后复检世界轴、零 rotate、层级、位置、元数据、容器设置和非目标 jointOrient；已匹配目标轴时计划为空。

Maya 2024 自生成 Y-Up 场景验证覆盖固定 `xDown/zForward`、只读预览、选择保持、元数据保持、幂等、一次 Undo 恢复，以及 `free` 在事务前拦截。World Match、轴交换、对称修正与自由 Forward 尚未进入合同。

## Maya 切片 12：free Forward 世界朝向

朝向快照新增 `FitOrientationAxisConfiguration`，以只读方式保存 FitSkeleton 可选的 `primaryAxis`、`secondaryAxis` 和 `worldmatch`；属性不存在时使用已确认的 X/Y/关闭默认值。轴枚举先转成带正负号的本地轴，并拒绝 primary/secondary 同轴配置。它们没有被加入容器的必备设置，因此不会为了读取朝向而修改旧场景。

当 `worldOrientForward=free` 时，计划将目标到直接子级的向量投影到世界 XZ 平面，再让全局 `secondaryAxis` 沿该水平参考方向，同时保持 worldOrient 指定的本地 Up 轴朝向世界 `+Y`，最后补全右手系第三轴。子级与目标在水平方向重合时无法确定 roll，计划会在事务前失败；固定 Forward 仍沿用世界 `+Z`。

Maya 写入器继续复用切片 11 的矩阵、后代位置补偿、单次 Undo 和构建后复检。Maya 2024 自生成斜向单子链验证覆盖 free 的只读计划、世界轴结果、位置保持、幂等与 Undo；同时确认 `worldmatch` 开启时不会进入当前写入器。World Match、轴交换与对称修正仍未实现。

## Maya 切片 13：显式分支子级朝向

`FitOrientationRequest.child_selections` 用 `FitOrientationChildSelection(parent, child)` 明确多子级关节的 Aim 分支。唯一子级仍可省略；存在多个直接 joint 子级时，缺少选择、父关节未包含在目标中、子级不存在或不是直接子级都会在事务前失败。计划不复制中心线、DAG 顺序或名称偏好的隐式选择规则。

`FitOrientationChange` 现在记录全部直接子级的原始 jointOrient。单子链继续使用已验证的 Maya joint 朝向命令；多分支使用计划生成的完整 X/Y/Z 世界矩阵，避免 Maya 命令自行选择第一个子级。两条路径都会恢复所有直接子级 jointOrient，并按父到子顺序恢复完整后代世界位置。

首次 Maya 2024 分支验证确认 Maya 的 joint 朝向命令不会服从外部选择的 Aim 子级，复检因此触发事务回滚。改为多分支矩阵路径后的隔离复验通过：显式 Clavicle 分支用于 Aim，兄弟 Spine 分支与 Clavicle 分支的 jointOrient、所有后代位置、选择、幂等计划和单次 Undo 均保持。分支自动推断、对称和特殊身体部位规则仍未进入合同。

## Maya 切片 14：通用模板事务与自生成上半身树

原 `CreateMinimalFitTemplate` 的创建、预检和复检逻辑提取为 `CreateFitTemplate`，调用方必须提供已经通过核心校验的 `FitTemplateSpec`。通用用例检查空容器、完整设置和全场景名称冲突，在一个 Undo Chunk 中按父级顺序创建全部 joint、写入标签，再逐项复检拓扑、局部位置、标签和容器设置。三关节入口作为薄兼容包装继续使用同一条执行路径。

`synthetic_upper_body_fit_template` 是独立设计的 14 关节 T-pose 测试树：Root、两节 Spine、Neck/Head/HeadEnd，以及左右 Collar/Shoulder/Elbow/Hand 链。Spine2 同时连接 Neck、ClavicleLeft 和 ClavicleRight，用于承载真实分支场景；Y-Up/Z-Up 只改变躯干方向，左右臂沿世界 X 展开，统一 `scale` 控制比例。模板完全由仓库代码生成，不读取、转换或提交授权安装中的身体模板。

Maya 2024 自生成 Z-Up 验证先复演三关节兼容入口，再在同一隔离进程中创建 14 关节上半身树，确认 Spine2 三分支、全部标签、只读预览、重复创建拦截、选择保持和单次 Undo。当前模板用于推进身体核心架构，不等同于完整人物 FitSkeleton；骨盆、腿、脚、手指、镜像和专用元数据尚未包含。

## Maya 切片 15：上半身创建与朝向单事务编排

`BuildSyntheticUpperBodyFit` 只负责编排已有的通用模板与显式分支朝向用例。它要求目标 FitSkeleton 位于根级、平移/旋转归零并锁定、缩放为一、设置完整且内部为空；这些条件与场景级重名检查都在任何写入前完成。

计划阶段用模板局部坐标预测完整绝对 DAG 路径和世界位置，再生成 11 个非末端关节的 X-Aim/Y-Secondary 变更。Spine2 的三个直接子级不会依赖 DAG 顺序或名称猜测，而是明确选择 Neck；直接子级列表在核心层排序，使预测与不同宿主返回顺序无关。

模板创建与朝向都提供受控的“事务内执行”入口，公开的独立用例仍各自保持原有单次 Undo 行为。组合用例只打开一个外层 Undo Chunk；关节创建完成后会重新采集真实场景并生成实际朝向计划，只有它与零修改预演完全一致才继续写入。创建复检、计划一致性或朝向复检任一失败，都会撤销本次创建的全部 14 个关节。

Maya 2024 独立 Z-Up 进程验证确认：预演不污染场景，14 个关节和 11 个朝向一次提交，Spine2 使用 Neck 分支，世界位置、零 rotate、选择与容器设置保持；重复构建在事务前被阻止，一次 Undo 删除整棵上半身树而保留容器和无关节点。本切片仍不加入骨盆、腿、脚、手指、镜像、World Match 或 Blender 实现。

## Maya 切片 16：单侧源腿与全身声明式编排

本机 MEL 清单中没有边界独立的腿部创建过程；相关更新集中在大型 Fit joint 更新器，完整身体则由外部 biped 模板导入。直接翻译该更新器会重新引入单体耦合。本切片只用本机已授权模板确认可观察的 `Root → Hip → Knee → Ankle`、Ankle 的 Heel/Toes 分支，以及 Toes 的足侧/末端分支；仓库不保存该模板、属性、数值或源码片段。

本切片最初在已有 14 关节上半身树上增加 8 个独立设计的源腿关节，用来验证 Root、Ankle 和 Toes 的多分支创建/朝向。位置由代码根据 Y/Z Up 和显式 scale 生成，不采用授权模板坐标。该临时 22 关节表示随后在镜像分析切片中被收敛为真正的单侧身体源树。

第十五切片的编排逻辑下沉为 `BuildOrientedFitTemplate`。任意已验证模板和 `FitOrientationRequest` 都可复用同一套容器预检、零修改预测、创建后计划复算、单事务提交与构建后复检；`BuildSyntheticUpperBodyFit` 继续作为兼容入口。新的 `BuildSyntheticBodySourceFit` 显式指定 Root→Spine1、Spine2→Neck、Ankle→Toes 和 Toes→ToesEnd，避免三处多分支依赖 DAG 顺序。

Maya 2024 独立 Z-Up 验证确认该临时表示的源腿/足部拓扑、标签、世界位置、零 rotate、选择和容器设置。重复构建在事务前停止，一次 Undo 删除整棵树但保留容器与无关节点。首次验证的业务复检已通过，结果汇总脚本因浮点完全相等误判；改为与 application 相同的 `1e-5` 容差后隔离复验通过。

## Maya 切片 17：构建期 M/R/L 对称拓扑展开

授权行为的可观察规则表明，FitSkeleton 保存中心链和单侧源分支，而不是保存两套对称 Fit joints。沿父链遇到的第一个偏离 X 中心面的关节决定整条分支的侧向：负 X 为 Right、正 X 为 Left；可镜像分支必须从 Right 开始。`noMirror` 使该分支只产生一侧，配合 `noMirrorLeft` 时改为只保留 Left。两项元数据会沿后代继承。

据此，`synthetic_body_source_fit_template` 收敛为 18 个关节：Root/Spine1/Chest/Neck/Head/HeadEnd 六个中心关节，Scapula/Shoulder/Elbow/Wrist 四个负 X Right 臂关节，以及 Hip/Knee/Ankle/Heel/Toes/FootSideInner/FootSideOuter/ToesEnd 八个负 X Right 腿足关节。此前用于朝向压力测试的 14 关节显式双臂模板仍作为独立测试入口，不参与构建期镜像。

核心 `expand_fit_symmetry` 在不导入 Maya 的情况下生成带 `_M/_R/_L` 后缀的逻辑输出路径、父子关系和世界位置。中心节点只产生 M；默认 Right 源分支产生 R 与 YZ 平面反射后的 L；`noMirror`/`noMirrorLeft` 规则按祖先传播。元数据不完整、配置冲突、非法中心容差或未标记的 Left 起始分支都会在产生构建计划前失败。`PlanFitSymmetry` 只负责从 Maya 适配器读取完整快照与设置，不修改场景。

Maya 2024 独立 Z-Up 验证确认 18 个真实 Fit 源关节只读展开为 30 个逻辑实例：6 M、12 R、12 L。输出父链、YZ 位置反射、Right 起始位置、选择保持和 Left-only 继承均通过；元数据一次 Undo 恢复默认展开，源树一次 Undo 完整移除，容器和无关节点保留。本切片不创建镜像 Fit joints，也不宣称已完成 Maya `mirrorBehavior` 朝向；下一切片将以此计划为输入开始物化构建骨架。

## Maya 切片 18：基础 Body skeleton 物化

本机清单中的完整骨架创建过程仍有 573 行，并与后续 Body rig 阶段相连。本切片没有迁移该过程，而是把上一个切片已经稳定的对称实例定义为唯一输入，只实现最早的 joint DAG 物化边界。`BodyJointSpec` 保存源 Fit joint、目标完整路径、父路径、M/R/L side、世界位置和标签；`BodySkeletonSnapshot` 保存 Maya 实际读取的相同状态以及 rotate/jointOrient。

`BuildBodySkeleton.plan()` 先执行只读对称展开，再读取全部源标签并扫描场景中 30 个目标短名。任一标签缺失或任一类型同名节点存在时都不会打开事务。执行时按父级优先顺序调用独立的 Body host 端口；创建后的纯 Python 审计逐关节核对集合、父子路径、side、标签、位置和中性朝向，并重新读取 Fit 朝向快照与容器设置，确保构建没有改写输入。

`MayaBodyBuildHost` 继承已验证的 Fit 读取与 Undo 基础设施，只实现 Body joint 创建和快照采集。它使用 `createNode(..., skipSelect=True)` 保持用户选择，显式写入 Maya joint side，并在父级下按世界位置放置每个关节。当前不调用旧骨架创建过程，不生成控制器、约束、IK、变形骨或显示层。

Maya 2024 独立 Z-Up 验证确认：18 个 Fit 源关节在场景零修改预演后生成 30 个 Body joints（6 M、12 R、12 L）；根、臂和腿的父链、世界位置、标签、side 与零 rotate/jointOrient 全部通过，Fit 输入和选择保持。二次构建因名称冲突在事务前停止，一次 Undo 只删除 30 个 Body joints，FitSkeleton、18 个源关节和无关节点继续存在。下一切片将单独研究并写入 Right/Left 镜像行为朝向。

## 不能依赖纯自动转换的部分

- MEL 全局变量跨过程共享，Python 模块命名空间不会自动等价。
- 字符串拼接的 `eval`、`evalDeferred`、按钮回调需要改成显式 callable。
- MEL 空数组、越界填充、命令返回值与 `maya.cmds` 的 `None` 行为不同。
- `catch/catchQuiet`、隐式选择集、当前父 UI 和 Maya 全局状态都需要明确建模。
- 过程之间存在大量按名字调用，机械分文件不会自动得到合理模块边界。

## 每次迁移的轻量验收

每个切片只保留三层证据：纯 Python 单元测试、同一输入场景的旧/新状态快照对比、一次独立 Maya GUI 生命周期烟雾测试。不会为每个过程建立重量级门禁；高风险构建与文件写入才增加专门场景。
